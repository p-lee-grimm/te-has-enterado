# Факты сущностей и сборка контекста

Полная спецификация — `SPEC-entity-facts.md` в корне репозитория. Здесь —
рабочий порядок.

Хранятся не готовые карточки, а **пул атомарных фактов**. Проверка факта
дорогая и разовая; сборка контекста под конкретный пост дешёвая и повторяется
каждый раз.

Аудитория — русскоязычные жители Испании без испанского политического
бэкграунда. Опрос показал: люди свободно читают по-испански, но не знают,
кто такой лидер оппозиции.

## Два инварианта

Всё остальное — детали реализации. Эти два нарушать нельзя:

1. **Ни одного утверждения без источника.** Каждый факт несёт дословную
   цитату, найденную в тексте источника автоматически. Собственные знания
   модели источником не являются никогда.
2. **Сборщик не изобретает.** Он выбирает и соединяет уже проверенные факты.
   Появление в собранной строке слова, которого нет в исходных фактах, —
   ошибка, а не вольность.

## Порядок работы

```
ИЗВЛЕЧЕНИЕ (разово на источник)
  sourcing.ladder → fact_extractor.md → validate_fact →
  fact_critic.md → verify_quotes → пул

СБОРКА (на каждый пост)
  пул + тема поста → fact_assembler.md → validate_assembly → блок в посте
```

Всё это уже реализовано в коде и запускается командами:

```bash
python manage.py fact extract <id>            # сухой прогон, ничего не пишет
python manage.py fact extract <id> --commit
python manage.py fact list <id>               # что лежит в пуле
python manage.py fact fix <номер> "новый текст"
python manage.py fact retire <номер>
python manage.py fact audit --send            # выборка недели владельцу
python run.py --refresh-facts --commit        # просрочка + перепроверка
```

Лимит итераций извлечения — **2**. Не прошедшие факты отбрасываются,
остальные из того же источника сохраняются. Отбрасывание факта не блокирует
сущность.

## Роли

**Извлекатель** (`prompts/fact_extractor.md`) не пишет связный текст. Он
возвращает атомарные утверждения: одно утверждение — один проверяемый факт.

**Критик** (`prompts/fact_critic.md`) не оценивает качество и не хвалит. Он
ищет для каждого факта дословный фрагмент источника. Два экземпляра одной
модели склонны соглашаться, поэтому критику даются вопросы с проверяемым
ответом, а **вердикт считает скрипт**: `facts.verify_quotes` ищет каждую
цитату в тексте и понижает `found` до false, если не нашёл. Критик не может
проштамповать себе pass.

**Сборщик** (`prompts/fact_assembler.md`) видит только пул и тему поста.
Источников он не видит вовсе — это структурная гарантия инварианта 2.

## Типы фактов

| kind | Что это | Атрибуция | Срок |
|---|---|---|---|
| `role` | должность, роль, чем руководит | нет | бессрочно |
| `scale` | масштаб и отрасль, качественно | нет | бессрочно |
| `classification` | «правоцентристская партия» | нет | бессрочно |
| `evaluative` | характеристика | **обязательна** | бессрочно |
| `legal` | процессуальный статус | нет | TTL 30 дней |

### Что запрещено во всех типах

- Рейтинговые места и числа: «786-я компания мира», «вторая по тиражу».
  Читателю не с чем сравнить, и они тухнут за год.
- Абсолютные суммы: состояния, капитализация, тиражи. Качественная оценка
  масштаба разрешена.
- Даты назначений, кроме случаев, когда сущность определяется именно ими.
- Оценочные прилагательные вне `kind = evaluative`
  (`config/blocklist.txt`).

### Атрибуция для evaluative

Укоренённость в источнике **не равна** нейтральности. «Ультраправый активист,
распространяющий фейки» полностью подтверждается цитатой из El País — и всё
равно недопустимо без атрибуции, потому что в блоке контекста прозвучит
от имени канала.

Факт с `kind = evaluative` содержит название издания прямо в тексте:
«El País описывает издание как часть ультраправой медиасреды». Это
проверяется механически.

**Размытая атрибуция запрещена наравне с оценочными словами:** «критики»,
«противники», «многие», «эксперты». Это способ произнести утверждение,
не отвечая за него, и он непроверяем. Список — `config/vague_attribution.txt`.

Самоописание — тоже `evaluative`, с атрибуцией на саму сущность. Появляться
в паре с чужой характеристикой не обязано: требование симметрии создаёт
ложный баланс там, где никто не спорит.

### Спорность решается разметкой полюсов

- Характеристика одинакова у источников **из разных бакетов** →
  `classification`, атрибуция не нужна.
- Источники разных бакетов **расходятся** → `evaluative` с именной
  атрибуцией, обе стороны отдельными фактами.
- Характеристика есть **только у одного бакета** → в пул не идёт, факт
  остаётся в статусе `candidate`. Это позиция лагеря, а не описание.

`evaluative` пишется, только если характеристика устойчива — верна и в
будущих сюжетах. Разовая реплика из конкретной новости остаётся в теле поста
как высказывание.

### Процессуальный статус

Формулировка берётся **только** из `config/legal_terms.yaml`, свободная
формулировка запрещена.

- `investigado` — **не** «обвиняемый». Термин ввели в 2015 взамен `imputado`
  именно из-за стигмы; русское «обвиняемый» её возвращает. Правильно:
  «фигурирует в расследовании».
- `condena no firme` — приговор не вступил в силу. «Осуждён» без оговорки —
  фактическая ошибка.
- Исход обязателен, если он есть в источнике. Оправдание — это текущее
  состояние, а не смягчающая деталь. Маркеры исхода —
  `config/legal_markers.txt`.
- Дело называется: «по делу Koldo», не «по делу о коррупции».
- Просроченный факт **не показывается** и встаёт в очередь на перепроверку.
  Формулировок «на момент публикации» не существует: молчание безопаснее
  устаревшего обвинения.

## Источники

`wiki` (es → ca → gl → eu → en) → `wiki_org` → `wikidata` → `official` →
`press`. Лестница — в `src/quepasa/sourcing.py`.

- **Подстановка сущности:** нет статьи о персоне, но есть о её организации —
  берём организацию носителем, роль персоны записываем фактом со ссылкой
  на статью организации. Проверка механическая: фамилия обязана встречаться
  в тексте статьи.
- **`official`** годится для каркаса, не для характеристики: ни одна партия
  не назовёт себя ультраправой. Ссылка ставится руками:
  `entity add … --official <url>`.
- **`press`** разрешает только `role` (должность как приложение при имени)
  и `evaluative` с атрибуцией. Никогда `scale`, `classification`, `legal`.
- Ничего не найдено → пула нет, показывается только `role_gloss`. Это
  штатный исход.

## role_gloss

Нижний этаж, покрывающий 100% сущностей. Возвращается тем же вызовом, что и
заголовок поста (`prompts/post_headline.md`), из статей кластера: в испанской
прессе роль почти всегда стоит приложением при первом упоминании.

Только должность или роль, 3–5 слов, своими словами, встраивается в
предложение. Никаких характеристик, даже если статья их даёт.

Читатель не должен встречать непонятное имя без пояснения — ни в первый раз,
ни в четвёртый. Порогов по частоте упоминаний не существует. Пост, где
сущность с `salience: primary` появляется без роли в тексте и без пула
фактов, не публикуется (`postgate._check_role_gloss`).

## Очередь entity_unresolved

Автосоздание сущностей запрещено: ошибка матчинга даёт дубликат, дубликаты
расходятся в фактах, разбирать дороже, чем заводить руками.

1. Читать по убыванию `count`: `python manage.py unresolved`.
2. Проверить, не алиас ли это существующей сущности — склонения, сокращения,
   испанское и русское написание.
3. Алиас → `manage.py entity alias`, новую сущность не создавать.
4. Новая → предложить создание с типом, создать после подтверждения:
   `manage.py entity add <id> --name-es … --type … --commit`.

## Аудит

Предварительное ревью упразднено: владелец не обладает экспертизой в
испанской политике, и кнопка «Ок» была ритуалом при сохранении полной
ответственности.

Вместо неё — 5 случайных фактов в неделю в чат ревью вместе с цитатой и
ссылкой. Владелец сверяет факт с фрагментом, что экспертизы не требует.
Плюс `fact fix` и `fact retire` с автоматическим откатом в посты последних
суток.

Правки владельца проверками не блокируются: он видит цитату рядом с фактом
и отвечает за формулировку сам. Непройденные проверки показываются как
предупреждение.
